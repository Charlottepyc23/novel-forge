> 状态：**①②③④ 全部已实施**（2026-08-22 定稿初版；晚完成 ①，深夜完成 ②，凌晨完成 ③④）

## 一、背景与问题

当前漫剧角色库 = 从小说角色库「刷新」而来，语义错位：

- **小说角色库**：全量文学角色（写作素材，谁被提及都算）
- **漫剧/短剧角色库**：制作角色（要建模、出图、锁一致性的"上镜角色"）

短篇（≤30 章）直接提取尚可；**长篇（100+ 章）全本提取不可行**（token 爆炸、角色爆炸、后期角色难覆盖）。

行业方案（2026-08 检索）：
- [alibaba/lumenx](https://github.com/alibaba/lumenx)：剧本分析阶段 LLM 提取角色/场景/道具 → 分镜脚本 → 角色三视图资产
- [Work-Fisher/ComfyUI-Novel-Director](https://github.com/Work-Fisher/ComfyUI-Novel-Director)：分镜 JSON 带 main_character 结构化引用角色名；角色名绑定参考图（IP-Adapter 锁脸）；casting 名册可串联扩展
- [UllrAI/CineGen-ShortDrama](https://github.com/UllrAI/CineGen-ShortDrama)：Script→Asset→Keyframe；每个角色生成标准定妆参考图，生成强约束
- [阿里云社区 ComfyUI 漫剧工业化](https://developer.aliyun.com/article/1755289)：IP-Adapter 人设锁定 + 时序稳色

**行业共识：角色提名发生在剧本/分镜阶段；分镜结构化携带角色引用；一致性靠定妆图绑定，不靠反复提取。**

## 二、目标架构（三级依赖链）

```
A. 小说角色库（全量索引）   ← 负责「发现」：全文提炼（现有 extractRoles 继续用）
B. 编剧产出（骨架/分镜表）  ← 负责「提名」：哪场戏谁上场
C. 漫剧角色库（投影子集）   ← 负责「制作」：谁建卡、谁定妆、谁出图
```

- C 不由 A 全量复制，由 B 提名、从 A 查询、投影到 C
- 长篇下 C 随剧情自然增长（分镜按集生成 → 提名天然局部化）

### 3.1 分镜表 / 骨架加结构化角色引用 —— ✅ 已实施（2026-08-22 晚）

```ts
// StoryboardShot 增加：
characters?: string[]   // 本镜头出镜角色（引用「小说库规范名」或漫剧卡名）
// StoryboardTable 增加：
characters?: string[]   // 本章全部出镜角色（去重）
// StoryboardSkeleton 增加：
characters?: string[]   // 骨架节拍涉及角色
```

- 生成分镜表/骨架时由 LLM 填写（与 beats 同步产出）✅
- 这是整个设计的**地基**：没有结构化引用，一切"按名匹配"都是猜谜
- 落地细节：
  - 骨架：LLM 输出 `characters`（正文确切称谓，3-10 个）；漏填时按角色库名命中正文确定性兜底
  - 分镜表：每镜头 LLM 输出 `characters`（1-4 个）；表级 `characters` = 镜头去重汇总，空则用骨架兜底
  - 视频提示词：镜头上下文注入「出场」行，供后续③绑定定妆图
  - 前端分镜工作台：骨架/分镜表/镜头卡均展示角色徽章，复制文本带出场角色

### 3.2 漫剧角色卡（MangaRoleCard）—— ✅ 已实施（2026-08-22 深夜）

独立存储（漫剧角色卡），保留来源关联（弱引用、只读快照，禁止反向写回小说库）：

```ts
interface MangaRoleCard {
  id: string
  sourceRoleName?: string   // 来源小说角色名（追溯用，非强外键）
  name: string              // 漫剧用名（可短剧化改名）
  identity: string
  coreFunction: 'protagonist' | 'mentor' | 'love_interest' | 'antagonist' | 'sidekick' | 'informant' | 'functional'
  protagonistRelation: 'enemy' | 'friend' | 'mentor' | 'lover' | 'exploit' | 'neutral'
  speechStyle: string       // 口头禅/说话方式（配音一致性）
  traits: string[]          // ≤3 个极致性格标签
  appearance: string        // 1-2 个辨识度外貌点
  keyScenes: string[]       // 3-5 个关键剧情节点
  appearsInEpisodes: number[]  // 上场集数
  status: 'pending_match' | 'pending_confirm' | 'imported' | 'anchored' | 'archived'
  // 形象资产（沿用现有）：imagePrompt / promptKit / imageUrl / gallery
}
```

落地细节（协议层 `MangaRoleCard` 与上图一致，另加 expressions/promptStyleId/createdAt/updatedAt）：
- 存储：`project.mangaRoles`（首版与小说角色库同级；后续可迁独立文件）
- 路由：`POST /manga/roles`，op = nominate / adopt / update / remove / visual / promptKit
- 锚点/精修复用小说角色库同款 LLM 管线（extractRoleVisualFrom / generateRolePromptKitFrom 底层抽象，漫画卡写回自身字段，status → anchored）

### 3.3 两级角色库（长篇小说）

- **C1 全局常驻**（≤10 人）：主角/大反派/核心配角——精做锚点、跨集锁定
- **C2 卷级/集级**：本卷上场配角/功能性角色——按需建卡、可跨卷复用；一次性路人**不上卡**（文字描述 + 通用模板直接出图）

## 四、流程与状态机（✅ 提名/匹配/导入已实施，定妆图回填属③）

```
分镜/骨架生成（带 characters[]）
   ↓ 漫剧工作台手动「从本集分镜导入角色」
候选角色名
   ↓ 规则过滤（精确名 + 身份简称/别名表，缩小到 3-5 候选）
   ↓ LLM 确认（是/否 + 选哪个，不做开放检索）
匹配到小说角色 → 复制为漫剧卡（sourceRoleName 关联，status=imported）
   ↓ 生成形象锚点 / 精修提示词（status=anchored）✅
   ↓ 回填分镜生成链路（定妆图绑定，IP-Adapter 类方案）✅（2026-08-22 凌晨）
未匹配：
   ├─ 小说里有但提炼漏了 → 提示回小说库补提炼
   └─ 漫剧新增角色 → 直接创建漫剧卡（不回写小说库）
```

状态机：待匹配 → 待确认 → 已导入 → 已定妆 → 已归档

触发时机（第一版）：漫剧工作台角色区「从本集分镜导入角色」手动按钮；后续可做分镜生成后自动提示。

## 五、边界规则

1. 匹配键不可靠 → 分镜必须结构化 characters[]（不做自由文本猜测）
2. 双向同步风险 → 漫剧卡独立存储，sourceRoleName 只读追溯，禁止回写
3. 跳集做分镜 → 允许乱序提名，但 C2 卡标注上场集数，按集排序展示
4. 匹配失败降级 → 明确判定提示：「回小说库补提炼」vs「漫剧直接创建」
5. 制作成本分层 → 路人不上卡；C1 精做、C2 按需
6. 匹配判定 → 规则过滤 + LLM 确认两段式（规则不裁决、LLM 不开放检索）
